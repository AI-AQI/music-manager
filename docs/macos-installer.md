# macOS 图形化安装器

版本：v0.2.6，包含图形化安装器、应用内更新和历史音乐库升级保护。数据库 schema 保持为 3。

## 使用流程

打开 DMG → 双击「安装与更新声场档案」→ 点击「安装 / 更新」。失败时在同一窗口重试、恢复旧版或导出诊断 ZIP。保留 DMG 以便以后重新打开安装窗口。

首次安装使用 `~/Applications`，更新优先保留已发现的 `/Applications` 安装位置。安装器只管理应用目录、其同级临时目录和 `.music-manager-backups` 备份目录，不搬迁音乐库。不会强制结束正在运行的应用；退出超时会停止替换。

## 已有数据库升级

安装保留应用标识 `com.musicmanager.app`、原位置配置及数据库文件。已有配置时，新版直接打开配置指向的同一个库，本机和移动硬盘上的库都无需重建、搬迁或重新导入。没有配置的历史默认库需要明确选择打开原文件夹，之后记住原路径；硬盘离线时停止并等待重试，不创建替代库。

结构升级之前用 SQLite 生成包含已提交 WAL 数据的完整备份。旧 Tag 结构首次使用 `library.pre-tag-tree-v1.db`，其他升级及再次尝试使用唯一命名的 `library.pre-schema-3-*.db`。备份失败则停止升级；旧备份不覆盖。建表、Tag 树转换、JSON Tag 转换、属性补齐、版本记录及外键校验在同一个事务中完成，任一步失败都撤销本次迁移。无效的旧 JSON Tag 会报错并保留原列，不按空标签删除。

迁移取得 SQLite 写锁后会再次检查 schema，防止等待锁期间其他版本已升级数据库，而旧进程随后把新版版本记录写回旧值。拒绝迁移时保留较新版本刚提交的数据和结构，并恢复当前连接的外键设置。

历史版本验证覆盖 v0.1.0 至 v0.2.5 的全部十个发布版本，分别测试本机目录与模拟外置目录，并保留含数据的 WAL 连接。校验原有音乐各字段、文件书签、播放记录、Tag ID 与层级、片段时间、专辑标签、候选清单、配置和音频字节；新版继续编辑后重新打开同一库，备份内容也与迁移前一致。样本来自对应发布提交的数据库初始化代码，不读取用户真实数据库；测试目录模拟外置盘，不等同于实体硬盘插拔测试。

## 安全替换与恢复

- 校验应用身份、完整签名、系统最低版本、CPU 架构和版本；禁止普通更新降级。
- 先复制到目标目录同级的唯一临时目录并校验，再正常退出主应用、保留旧版、替换。
- 更新记录位于 `~/Library/Logs/com.musicmanager.installer/latest.json`；同一用户仅允许一个安装器执行。记录损坏时停止修改，仍可导出诊断。
- 替换阶段失败会尝试恢复旧版；恢复也失败时保留备份并报告位置。
- 新版已移入目标位置、但 `installed` 状态尚未保存时中断，重新打开安装器后可通过「重新尝试启动」或「安装 / 更新」继续。先核对身份、版本、完整签名和启动协议，再沿用原事务确认启动，不覆盖原备份；暂存应用仍存在或校验失败时不推进状态。
- Apple Silicon 上恢复 Intel 旧备份时，通过系统程序检查 Rosetta 实际可用性，再执行数据库兼容性预检；不提前启动旧应用。Rosetta 不可用或数据库不兼容均停止恢复并保留副本。新下载的安装包仍要求原生架构。
- 新版一旦替换就位，恢复前必须只读检查音乐库 schema；不依赖安装器的启动记录，用户从 Finder 手动启动也适用。版本过新、无法读取配置或硬盘不在线均拒绝恢复；不回滚数据库。只有新版仍在暂存位置、尚未替换就位时，才允许直接恢复原应用。
- 恢复前保存恢复阶段，新版保存在本次备份目录中的固定暂存路径。两次移动之间中断可继续恢复；旧版已移回但完成记录未写入时，可确认恢复完成。恢复重试会重新检查数据库兼容性。
- 已发布的 0.2.5 支持 schema 3 和缺盘启动保护。更早版本缺少确认信息，新版替换就位后不会自动恢复它们。
- 备份不会自动清理；多次更新会占用额外空间。只通过窗口恢复最近一次更新，更早备份留在磁盘上。
- 新版启动失败时，可安装版本更高的修复包；原始及中间应用备份均保留，先前事务归档到日志目录的 `transactions`。同版本重装和未完成的恢复仍受保护，不绕过数据库兼容性检查。
- 已安装新版损坏时，恢复可使用独立验证通过的安装包内应用执行只读数据库兼容性预检；没有可信检查程序或数据库不兼容时停止，保留所有副本。
- 已完成的安装记录不会锁定旧应用位置；应用在两个受支持目录间移动后可继续更新，旧记录归档，未完成事务仍要求先处理。
- 管理员授权按实际修改目录判断：创建多层备份目录检查最近的已有父目录，移动应用同时检查源和目标目录。需要时仅提升对应应用文件操作，数据库兼容性预检仍以当前用户只读运行；取消授权停止替换并保留原应用和音乐库。

## 启动确认与诊断

安装器为本次启动生成独立令牌，同时核对进程 ID、版本和状态。主应用回报界面就绪、待选库、库不可用、主动退出或失败；进程存活本身不代表启动成功。等待超过 45 秒时显示「尚未确认」，不强杀或自动降级。安装确认只覆盖启动阶段，不保证后续运行永不崩溃。

每次启动的输出、状态、时间和错误分别保存在当前更新事务的独立启动目录中。点击重试或关闭后重新打开安装窗口不会覆盖之前的失败记录。

ZIP 包含安装日志、本次更新的各次启动输出、状态与更新记录，以及可读取的最近一份 `music-manager` 崩溃报告（它可能早于本次更新）。不包含数据库、settings.json 或音频。内容可能含本机路径，用户自行决定分享对象；不会自动上传。

## 验证记录与限制

- Rust：数据库只读恢复预检，包括 SQLite WAL 内的新 schema、缺盘、损坏配置；与原有启动/切换保护一并测试。
- JavaScript：启动与库切换回归，验证新增启动状态上报。
- Swift：复制失败、替换失败恢复、应用拒绝退出、降级拒绝、兼容性拒绝、恢复、未完成事务、并发安装锁、损坏记录、陈旧启动报告及真实子进程提前退出；另覆盖恢复两个移动边界的中断、恢复重试时兼容性变化、Finder 手动启动、未就位的旧版恢复，以及跨窗口重试后 ZIP 中所有失败日志保留。
- 本机 Apple Silicon 原生窗口实测：隔离应用更新、首次选择并创建测试库、重试启动确认 ready、恢复旧应用、导出 ZIP。恢复前后的数据库逻辑内容一致，ZIP 无数据库或音频。
- 原生界面测试使用独立应用标识和 `/private/tmp/music-manager-installer-ui`，没有更新用户的正式应用。替换的两个测试应用版本相同；跨版本恢复边界由回归测试覆盖。
- Intel 的真实机器安装、管理员授权、不同 macOS 版本的 Gatekeeper 首次放行尚未实测；CI 已配置两个架构分别构建。免费 ad-hoc 签名仍可能触发系统拦截。
- 二次 review 修复增加 13 项回归用例，安装器共 43 项测试通过：覆盖已替换但未落盘后的两种继续入口及真实子进程启动确认、身份/签名/版本/协议异常拒绝、暂存边界，以及模拟 Rosetta 可用/不可用、数据库不兼容和恢复中断。系统 Rosetta 探测命令也已在本机执行成功；架构恢复矩阵使用模拟系统返回值，不等于 Intel 实机验证。
- 后续增加 10 项安装器回归用例，共 53 项通过：覆盖损坏程序使用独立检查器恢复、兼容性与签名拒绝、更高修复版接续三种未完成状态、终结事务的目录移动及未完成事务保护。Rust 新增历史数据库矩阵、旧默认库选择、JSON Tag 转换和整次迁移失败回滚测试。
- 并发与权限修复新增 1 项 Rust、4 项 Swift 回归测试；当前 Rust 共 51 项、安装器共 57 项通过。并发测试用真实 SQLite 双连接和锁等待回调控制竞争顺序；权限测试使用隔离的受限目录与模拟管理员授权，覆盖备份祖先目录、恢复的源/目标目录、取消授权和正常无授权路径，不代表完成了真实系统授权窗口验证。

主应用 schema 变更时需同步 `src-tauri/Info.plist` 的 `MusicManagerDatabaseSchema`；打包脚本会检查二者一致。`INSTALLER_UI_TESTS` 仅用于隔离测试构建，发布脚本不会启用。

## 应用内更新

主界面右上角「更新」→ 检查版本 → 下载 → 保存编辑 →「重启并更新」。首次支持此功能的版本仍需通过 DMG 安装；已经发布的 v0.2.5 不会凭空出现更新入口。

下载使用 [Tauri 官方更新插件](https://v2.tauri.app/plugin/updater/)，读取 GitHub 最新 Release 的 `latest.json`。Apple Silicon（包括 Rosetta 下运行的旧 Intel 应用）选择 `darwin-aarch64`，Intel 选择 `darwin-x86_64`。只接受本仓库、明确版本及对应架构的 HTTPS 下载地址。

- 下载完成后验证独立更新签名，重启前再次验证本地缓存。签名公钥随应用发布；这与 Apple Developer ID 签名、公证不同，不需要 Apple 会员。
- 整个 DMG 都经过签名；执行前还核对安装器与内嵌应用的身份、实际版本及更新协议，防止更新清单把旧的签名包冒充新版。
- 主应用等待在途命令完成并阻止新的库操作，再把安装器复制到独立缓存目录。安装器确认包和安装位置后回复本次令牌、PID、版本；主应用收到匹配回复才退出。
- 安装器必须等原进程退出后才替换文件。随后复用安全备份、恢复和启动确认流程；正常完成后关闭安装窗口。失败则保留恢复及导出诊断入口。
- 开发模式、DMG 内或自定义路径的应用不原地升级；只支持 `/Applications/声场档案.app` 和当前用户 `~/Applications/声场档案.app`。
- 缓存位于应用的 `Library/Caches` 目录；独立安装器与下载包保留供排查，不保存在音乐库目录。

### 签名密钥与首次发布配置

项目只保存公钥 `src-tauri/updater-public-key.txt`，并在 `tauri.conf.json` 中配置相同公钥。本机生成的生产私钥保存于 `~/.config/music-manager/updater.key`，文件权限为 600，不在 Git 仓库中。

发布前需在 GitHub 仓库的 Actions secrets 中设置 **`TAURI_SIGNING_PRIVATE_KEY`**，值为该私钥文件的内容。当前生成的密钥不设口令，工作流的 `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` 留空。工作流会检查 Secret 并验证签名与内置公钥匹配，缺少或不匹配时停止发布。请备份私钥；已经安装的应用只信任随它发布的公钥，后续不能随意重新生成一套密钥。

发布工作流在两个原生 Mac runner 上分别构建 DMG，签名后再用应用内置公钥验证。签名缺失、错误密钥、缺少任一架构时拒绝发布更新清单。Release 同时包含两个 DMG、各自 `.sig` 和 `latest.json`；发布前修改 `docs/update-notes.txt`，作为 App 内显示的更新说明。

本地签名与验证（替换具体 DMG 路径）：

```bash
TAURI_SIGNING_PRIVATE_KEY_PATH="$HOME/.config/music-manager/updater.key" \
TAURI_SIGNING_PRIVATE_KEY_PASSWORD="" cargo tauri signer sign /absolute/path/update.dmg
cargo run --locked --manifest-path src-tauri/Cargo.toml --example verify-update -- \
  /absolute/path/update.dmg /absolute/path/update.dmg.sig
```

应用内更新测试：`node --test scripts/test-updater.cjs scripts/test-database-switch.cjs`；更新清单测试：`python3 scripts/test-update-manifest.py`。签名篡改、错误公钥、并发请求、架构和地址匹配由 Rust 测试覆盖；安装器交接和退出等待由 Swift 测试覆盖。正式 GitHub Release 的在线升级链路需在配置 Secret 并发布首个支持更新的版本后验证。

另已在本机进行真实进程交接测试：隔离旧应用的测试版本标记为 0.2.4，新包为 0.2.5；助手回复就绪时旧应用未被修改，父进程退出后自动备份、替换并启动新版，收到 `ready` 后退出。检查确认旧版本备份存在，测试库逻辑内容完全一致。该测试使用当前代码构建的隔离应用，不代表已验证历史 0.2.4 二进制或正式 GitHub 下载链路。调试版 Dock 图标改为内嵌，避免启动时读取源码目录触发文件访问等待。
